# 商城系统安全稳定性与性能优化计划

## 目标

在不重写现有 RuoYi 单体、Vue 3 管理端和原生微信小程序的前提下，将当前“可联调”的商城提升到“可受控上线”状态。本计划优先处理安全、资金、订单、库存和会话正确性，再处理查询、构建体积和历史模块。

本计划延续以下已有设计，不另建一套商城模型：

- [商城运营后台落地计划](./2026-07-24-商城运营后台落地计划.md)
- [商城数据库关系表设计计划](./2026-07-27-商城数据库关系表设计计划.md)
- [农产品小程序前后端打通计划](./2026-07-27-农产品小程序前后端打通计划.md)

## 实施原则

1. **P0 没有清零前不上线**：前端体积、代码格式和普通 CRUD 优化不得挤占安全与交易闭环时间。
2. **修共享根因**：订单状态、库存、券和审计在 Service 层统一修正，不在后台和小程序 Controller 分别打补丁。
3. **不重写已有结构**：继续复用 Spring 事务、MyBatis 条件更新、Redis、RuoYi 权限与日志、Vue 3 和原生小程序。
4. **金额与事实只在服务端裁决**：客户端不能更改价格、运费、优惠、会员 ID 或订单状态。
5. **不为优化预建业务表**：首页、N+1 和包体优化优先改查询与删除旧代码；只有 `EXPLAIN` 和真实负载证明需要时才加索引。
6. **数据库变更先落文件**：执行任何 DDL/DML 前，先在 `sql/update/` 创建完整的 `xxxx-xx-xx-描述.sql`，复核后再执行；禁止未落盘的内联 SQL。
7. **非平凡逻辑必须留一个可运行检查**：交易、认证和批处理使用真实测试，不得只增加正则源码合约。

## 阶段 0：密钥处置与生产冻结

### 目标

先使已泄露的凭据失效，再修配置文件。历史清理不能代替密码轮换。

### 任务

1. 立即轮换 `application-druid-copy.yml` 中曾出现的数据库账号密码，核对该账号最近登录、异常查询、用户与授权变更。
2. 轮换管理端 token 密钥、Druid 控制台密码以及任何复用了相同值的环境。
3. 从跟踪文件中删除真实主机和密码，默认值只保留无权限的本地开发示例，生产密钥缺失时必须启动失败。
4. 评估 Git 历史清理；如果仓库已有其他克隆或镜像，先协调团队再重写历史。无论是否重写，都必须完成凭据轮换。
5. 在 P0 处理完毕前冻结生产发布和对公网暴露的联调环境。

### 验收

1. 旧数据库密码、token 密钥和控制台密码全部失效。
2. `git grep` 和历史扫描不再发现仍然有效的秘密。
3. 不提供环境密钥时，生产 profile 拒绝启动，而不是使用仓库默认值。

## 阶段 2：交易一致性修复

### 2.1 SKU 全量同步

1. 在商品更新事务内先查询原有 SKU ID，校验提交的旧 SKU 全部属于当前商品。
2. 新 SKU 使用现有 `insertSku`，保留“新建库存为 0，必须通过入库命令增加”规则。
3. 提交的旧 SKU 使用带 `product_id` 条件的更新，不允许通过伪造 SKU ID 修改其他商品。
4. 对“原有但本次未提交”的 SKU 做软删除或停用；存在锁定库存时拒绝删除，已有订单明细由快照保留历史。
5. 后端返回“SKU 不存在、不属于当前商品、有锁定库存”等可读错误，不依赖数据库通用异常。

### 2.2 超时关单事务

1. `closeExpiredOrders()` 只负责分批扫描和统计，不在整批外层开启一个长事务。
2. 复用 Spring `TransactionTemplate` 对每笔关单单独开启事务；在事务回调外捕获单笔异常，确保状态、库存、优惠券和流水全部成功或全部回滚。
3. 重复扫描已取消订单时返回最终状态，不重复释放库存、解锁券或写相同流水。
4. 单笔失败记录订单号、错误类型和追踪信息，不记录收货地址、完整 token 或密钥。
5. 任务返回扫描数、成功数和失败数，失败订单在下一轮可重试。

### 2.3 状态和审计语义

1. 订单取消、支付、发货和完成命令显式接收 `operatorType` 和 `operatorId`，只允许 `MEMBER/ADMIN/SYSTEM`。
2. 小程序取消和确认收货记录 `MEMBER`，超时关单记录 `SYSTEM`，管理端操作记录 `ADMIN`。
3. 状态更新继续使用“主键 + 旧状态”条件；影响行数为 0 时重新读取状态区分幂等重试和非法跃迁。
4. 会员接口不接收客户端 `memberId`，管理端敏感信息继续使用独立权限。

### 2.4 会员会话立即撤销

1. Redis 中增加“会员 ID -> token 集合”的反向索引，登录、退出和过期时保持索引与 token 一致。
2. 后台将会员状态改为禁用时，同步删除该会员所有 token；从禁用恢复正常不自动签发新会话。
3. 会话撤销失败时后台状态更新不能假报完全成功；记录告警并支持重试撤销。
4. 会员订单写入前仍保留数据库活跃状态检查，不仅信任 Redis 会话。

### 2.5 防止恶意锁库存

1. 为订单预览和创建请求的 `items` 增加最大条数，合并相同 SKU 后再校验单 SKU 数量和订单总数量。
2. 在 Service 中查询当前会员未过期待支付订单数和已锁数量，达到上限时拒绝继续创建。
3. 复用现有 Redis `@RateLimiter` 限制短时间高频创建；网关或注解无法稳定以会员 ID 为维度时，以 Service 层待支付上限作为最终保护，不只按 IP。
4. 保留 `(member_id, client_request_no)` 唯一约束，并处理两个并发相同幂等号的唯一键冲突：回读已有订单，不向客户端返回通用 500。
5. 频控、待支付上限和锁定上限使用现有 `sys_config`，先给保守默认值，再根据真实转化率调整。如需初始化配置 DML，必须先创建 `sql/update/2026-08-xx-新增商城交易保护配置.sql`。

### 验收

1. 编辑商品删除一个无锁定库存 SKU 后，管理端详情和小程序都不再返回该 SKU。
2. SKU 有锁定库存时删除失败，商品和其他 SKU 不发生部分更新。
3. 任意一笔超时关单在释放库存或解锁券时失败，该订单状态保持待支付；同批其他订单可独立成功。
4. 会员取消、管理员取消和系统超时关单的订单日志分别显示 `MEMBER/ADMIN/SYSTEM`。
5. 后台禁用会员后，已签发 token 的下一个请求返回 401，恢复会员后必须重新登录。
6. 超出待支付订单或锁定库存上限时创建失败，不产生新订单、库存流水或锁券。

## 阶段 3：微信支付闭环

### 前置条件

以下任一条件缺失时，只能验收到“真实待支付订单”，不能宣称支付已打通：

1. 已认证小程序 AppID。
2. 已关联可用的微信支付商户号。
3. 公网 HTTPS API 域名和微信可访问的支付通知地址。
4. 商户私钥、证书序列号、API v3 密钥和微信支付公钥或平台证书。

### 任务

1. 按《农产品小程序前后端打通计划》约定，使用与 Java 8 兼容的微信支付 API v3 官方 Java SDK，不手写签名、验签和通知解密。
2. 实现会员订单支付参数接口，只允许当前会员的未过期待支付订单创建或复用预下单。
3. 小程序识别后端 `availableActions` 中的 `PAY`，调用 `wx.requestPayment`；无论客户端成功、失败或取消，都重新读取服务端订单状态。
4. 支付通知接口允许微信匿名调用，但必须使用原始请求体和微信请求头完成验签、解密、AppID、商户号、订单号和金额核对。
5. 支付事务幂等更新订单，将锁定库存转为实扣、优惠券转为已使用，并写库存流水和订单日志。
6. 超时任务对已有预支付单的订单先调用微信关单；遇到已支付则查单并转入支付成功处理，不允许本地先释放库存。
7. 将管理端人工 `pay-success` 改为受控补单流程，或在生产完全禁用；人工补单前必须查询支付渠道，不直接信任前端传入的渠道单号和金额。
8. 仅当订单应付金额为 0 时允许 `FREE` 状态迁移，仍执行库存实扣、券核销和日志写入。

### 验收

1. 小程序可从待支付订单首次或再次拉起微信支付。
2. 客户端伪造支付成功、金额不符、签名错误、AppID/商户号不符都不改变订单状态。
3. 相同支付通知重复投递不重复实扣库存、核销券或累加成交额。
4. 支付通知与超时关单并发时，最终只能是“已支付且库存实扣”或“已关单且库存释放”之一。
5. 订单日志、服务日志和小程序包中均不出现私钥、API v3 密钥、AppSecret、完整 token 或支付通知明文。

## 阶段 4：真实测试与持续验证

### 验收

2. 人为破坏库存回滚、SKU 删除、会话撤销或支付幂等的任一逻辑，对应测试会失败。
3. Pull Request 在测试或生产构建失败时不能合并。
4. CI 日志不输出数据库密码、token、微信密钥或支付通知明文。

## 阶段 5：查询与前端体积优化

### 5.1 公开商城查询

1. 首页不再调用全量商品列表后在 Java 截取。
2. 最新商品按 `publish_time DESC, product_id DESC LIMIT 8` 独立查询。
3. 热销商品使用已支付订单明细的近 30 天销量聚合，真实无成交时返回空列表或明确回退到最新商品，不把最新伪装成热销。
4. 商品列表继续使用 PageHelper 分页，首页专用查询直接在 SQL 限制行数。

### 5.2 消除 N+1

1. 会员订单列表先分页取订单，再使用当页订单 ID 一次查询所有明细，按 `order_id` 分组组装 DTO。
2. 公开优惠券列表在已登录时一次查询当前会员已领取的 `coupon_id` 集合，不逐券 `COUNT`。
3. Mapper 的 `IN` 参数只来自已分页的服务端 ID 集合，空集合直接返回，不生成无边界 SQL。
4. 优化前后使用同一数据集记录 SQL 次数和总耗时，证明改动收益。

### 5.3 管理端包体

1. 先完成“公交模块去留”决策；不需要的图表类型通过删除历史页面自然消失。
2. 将 ECharts 注册按业务页面分开，商城首页只注册实际使用的折线图、柱状图和必要组件。
3. 评估 Element Plus 组件按需引入；只在构建体积测量能证明明显收益时实施，不为了消除告警而增加大量自动导入配置。
4. 继续使用路由动态导入和现有 gzip；`manualChunks` 只用于缓存边界，不将“分包”误当成“减少字节”。
5. 用产物体积、gzip 体积和真实首页请求记录优化结果，不只比较源码行数。

### 验收

1. `/app/shop/home` 不随全部商品数量线性返回数据，最新与热销排序可由真实数据解释。
2. 100 条订单的列表明细查询由最多 101 次降为固定 2 次主查询，不含 PageHelper 的计数查询。
3. 优惠券已领状态不再随券数量增加 SQL 次数。
4. 管理端产物比当前 6.2 MB 基线有可量化下降，商城首页和常用管理页功能不回归。

## 阶段 6：历史模块决策与清理

### 决策门

实施前由产品负责人确认：“公交客流分析是否仍属于黔山优选商城的生产范围？”

### 路径 A：不再需要公交能力（推荐）

1. 从根 `pom.xml` 的 modules/dependencyManagement 和 `ruoyi-admin/pom.xml` 删除 `ruoyi-JnBusViz`，再删除该模块。
2. 删除 `RuoYi-Vue3/src/views/visualization`、公交专用组件、常量路由和不再使用的 ECharts 类型。
3. 将 `sql/system_menu_routes_rebuild.sql` 中的公交菜单作为历史脚本标记或删除；对已有数据库的菜单清理必须另写 `sql/update/` DML 脚本。
4. 删除小程序未注册的 `pages/work`、只为该页服务的 `utils/mock.js` 和已确认无引用的旧图片。
5. 删除后用 `rg` 确认无残留导入、路由、菜单和标题，再执行 Maven 和 Vue 生产构建。

### 路径 B：仍需要公交能力

1. 不在商城导航中暴露公交路由，为公交 Controller 和页面补独立权限。
2. 优先拆为独立部署或独立前端入口，商城不打包公交大屏代码和无关 API。
3. 在未完成拆分前，至少将公交模块标记为独立可选 profile，并对构建体积、启动时间和暴露接口单独测量。

### 验收

1. 仓库中只保留产品责任范围内的业务模块。
2. 未授权商城管理员无法访问公交 API 或大屏路由。
3. 管理端标题、登录页、菜单、README 和小程序名称只描述当前产品。

## 数据库变更边界

当前已确认的 SKU 同步、事务分割、会话撤销、N+1 和包体优化可以不改表结构。以下情况才生成增量 SQL：

1. 新增交易保护 `sys_config` 配置。
2. 支付实现证明现有 `pay_prepay_id`、渠道单号和时间字段不足。
3. `EXPLAIN` 和基准测试证明现有索引无法支持最新商品、热销聚合或待支付会员上限查询。
4. 清理已有数库中的公交菜单或旧权限。

每个数据库变更都必须使用单独的 `sql/update/xxxx-xx-xx-描述.sql`，包含前置检查、可重复执行边界、影响范围和手工回滚说明。禁止为了方便测试直接向共享库插入假订单或伪造支付数据。

## 发布与回滚

1. **配置先行**：先准备新密钥、域名、文件目录和网关规则，再发布代码；不在新代码上线后再临时找密钥。
2. **备份和核对**：涉及数据库前备份目标库，记录订单状态、SKU 可用/锁定库存、券状态和流水基线。
3. **小步发布**：安全配置、交易修复、支付、查询优化和历史清理分别发布，不合并成一次无法定位的大发布。
4. **交易修复观察**：重点监测创建订单失败率、库存锁定/释放差异、关单失败、支付通知重试和会话 401 增量。
5. **代码回滚不回退交易事实**：不通过删订单、删流水、手改库存或伪造支付状态回滚；如有数据修复，先生成专用 SQL 文件并双人复核。

## 整体验收标准

### 安全

1. 仓库、前端产物、小程序包和 CI 日志中没有仍然有效的数据库、Redis、token、微信或支付秘密。
2. 生产 Swagger/Druid 不对公网匿名开放，会员和管理员身份不可互换。
3. 禁用会员的旧 token 立即失效，任意会员无法访问他人地址、券或订单。

### 交易正确性

1. 相同幂等号的并发请求只产生一个订单、一次库存锁定和一次优惠券锁定。
2. 创建、支付、取消、超时、发货和收货的每个状态迁移要么完整成功，要么完整回滚。
3. 库存不为负，`available_stock + locked_stock` 的变化可以由唯一流水还原，券不重复使用。
4. 支付状态只来自经验签且核对金额的微信通知/查单或严格受控的补单流程。
5. 会员、管理员和系统任务的状态变更日志归属正确。

### 质量与性能

1. Maven 有会对业务回归失败的真实测试，Node 合约测试有标准 `npm test` 入口，CI 自动执行测试和构建。
2. 首页查询有服务端行数上限，最新和热销有不同且可解释的口径。
3. 订单明细和优惠券领取状态没有 N+1 查询。
4. 前端产物体积和关键页加载相比 2026-08-07 基线有测量记录，没有通过调大 Vite 告警阈值假装优化。

### 产品完整性

1. trial/release 小程序使用真实 HTTPS 域名，可完成登录、浏览、加购、地址、领券、下单、支付、发货和收货。
2. 品牌、菜单、路由和 README 不再同时出现商城、公交分析和 RuoYi 演示名称，除非已明确选择多产品路径 B。
3. 未提供真实支付前置条件时，项目文档和 UI 明确停在待支付，不伪造付款成功。

## 非目标

本轮不顺手增加以下能力：

1. 多商户、分账、多仓、WMS 或第三方物流平台。
2. 部分发货、复杂运费模板、冷链、预售、称重计价或团购。
3. 退款、售后、直播、分销或会员等级；这些需要独立业务设计，不塞进当前订单状态。
4. 为了“看起来现代”整体重写 Java、切换小程序框架或引入新的全局状态库。
5. 在没有兼容性评估和回归测试前同时升级 Java、Spring Boot、Vue、Vite 和整套依赖。技术栈升级应在交易闭环稳定后单独立项。

## 建议执行顺序

```text
凭据轮换与发布冻结
    -> 生产配置收口
    -> SKU/关单/会话/防锁库存修复
    -> 交易和认证真实测试
    -> 微信支付闭环
    -> CI 和标准检查入口
    -> 首页/N+1 查询优化
    -> 历史模块决策与删除
    -> 包体与技术栈后续优化
```

实施时每个阶段单独提交、单独验收。P0 完成、交易一致性测试通过、真实支付或明确的“不开放交易”边界确认之前，不进入生产发布。
